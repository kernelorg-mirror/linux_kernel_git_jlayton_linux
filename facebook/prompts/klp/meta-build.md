# Meta KLP Build Pipeline

## Overview

Meta builds KLP modules using `kpatch-build` via Buck2. The pipeline:

1. Two git tags define the patch: `<from_tag>` (baseline) and `<to_tag>` (must end in `-hotfix<N>`)
2. Baseline and target source trees are checked out
3. Kernel-devel and kernel-bin RPMs for the baseline are downloaded via `kerctl`
4. `kpatch-build` runs inside a container to produce the `.ko` module
5. Optionally signed with `autograph_client.par`
6. Packaged as RPM, installed to `/var/lib/kpatch/<kernel-version>/`

## Build Files

| File | Purpose |
|------|---------|
| `facebook/bzl/klp.bzl` | Buck2 build rules -- main orchestration |
| `facebook/bzl/constants.bzl` | URIs/hashes for kpatch-build RPM, PGO data, build images |
| `facebook/build/klp.spec` | RPM spec for packaging the KLP module |
| `facebook/build/TARGETS` | Buck2 target definitions including `kpatch-build-rpm` |
| `facebook/9999-Dummy-patch-to-bump-hotfix-version.patch.template` | Template setting `HF_VERSION` in `include/hotfix/hotfix.h` |

## Build Commands

**Always check out the hotfix tag before building.** The tag contains
required build infrastructure changes (e.g., `klp.bzl`, `constants.bzl`)
that must be present in the working tree for the build to succeed.

**Always clean the build folder first:**
```bash
git checkout <hotfix-tag>
sudo rm -rf buck-out/v2/
```

```bash
# Basic x86_64 KLP build (regular flavor, no --config klp.flavor needed)
buck2 build $(facebook/build/buck-config) \
  -c klp.patch_to=<hotfix-tag> //:klp-rpm

# With explicit flavor (only if non-regular flavor is needed)
buck2 build $(facebook/build/buck-config) \
  -c klp.patch_to=<hotfix-tag> \
  -c klp.flavor=<flavor> //:klp-rpm

# For aarch64
buck2 build $(facebook/build/buck-config) \
  -c klp.arch=aarch64 \
  -c klp.patch_to=<hotfix-tag> //:klp-rpm

# With module signing
buck2 build $(facebook/build/buck-config) \
  -c kernel.sign_mod=true \
  -c kernel.sign_mod_key=<key-name> \
  -c klp.patch_to=<hotfix-tag> //:klp-rpm
```

Notes:
- The target is `//:klp-rpm` (root TARGETS, generated by `klp()` call)
- `facebook/build/buck-config` outputs required build-info flags (kernel version,
  git info) and also runs `buck2 clean` internally
- **After each successful build**, copy the `.ko` and `.rpm` artifacts to
  `klp-out/<arch>-<flavor>/` (e.g. `klp-out/x86_64-regular/`,
  `klp-out/x86_64-hardened/`, `klp-out/aarch64-regular/`).
  When building for **multiple kernel branches**, add the baseline tag as
  a parent directory to keep artifacts separated:
  `klp-out/<baseline-tag>/<arch>-<flavor>/` (e.g.
  `klp-out/v6.11-fbk10/x86_64-regular/`,
  `klp-out/v6.13-fbk12/aarch64-regular/`):
  ```bash
  mkdir -p klp-out/<baseline-tag>/<arch>-<flavor>
  cp buck-out/v2/gen/linux/*/__klp-build__/out/*.ko klp-out/<baseline-tag>/<arch>-<flavor>/
  cp buck-out/v2/gen/linux/*/__klp-rpm__/out/*.rpm klp-out/<baseline-tag>/<arch>-<flavor>/
  ```
- **NEVER run `facebook/build/buck-config` again after the build completes**
  (e.g., to inspect outputs with `--show-output`), because it triggers
  `buck2 clean` and destroys all build artifacts
- Always test **x86_64 regular** flavor first (the default, omit
  `klp.flavor` and `klp.arch`), unless the user explicitly requests a
  different flavor or architecture

**Required arch-flavor combinations for production KLPs:**

| # | Architecture | Flavor | Build flags |
|---|---|---|---|
| 1 | x86_64 | regular | (default, no extra flags) |
| 2 | x86_64 | hardened | `-c klp.flavor=hardened` |
| 3 | aarch64 | regular | `-c klp.arch=aarch64` |

**Note:** aarch64 KLP support was added in later kernel releases. Older
branches (e.g. v6.11 and earlier) only support x86_64 -- `klp.bzl` will
fail with `"Only x86_64 is supported for klp"` if you attempt an aarch64
build on those branches.

**Each flavor must be built separately.** Clean `buck-out/v2/` between
each build, and copy artifacts to `klp-out/<arch>-<flavor>/` immediately
after each successful build (before the next clean wipes them).

## Build Parameters (set via `--config`)

| Parameter | Description |
|-----------|-------------|
| `klp.patch_to` | Tag to patch to (must end in `-hotfix<N>`) |
| `klp.patch_from` | Tag to patch from (defaults to `patch_to` minus `-hotfix<N>` suffix) |
| `klp.flavor` | Kernel flavor |
| `klp.label` | Build label |
| `klp.arch` | Architecture: `x86_64` (default) or `aarch64` |
| `kernel.sign_mod` | `true` to sign the module |
| `kernel.sign_mod_key` | Signing key name (default: `hsm-test-key`) |

## kpatch-build Workarounds (in klp.bzl)

The build patches `kpatch-build` itself for newer kernels:

1. **`--save-scmversion` removal** -- `setlocalversion` changed in 6.4 (`f6e09b07cc12`), removing this flag
2. **`init/version-timestamp.o` exclusion** -- introduced after 5.19 (`2df8220cc511`), varies between builds
3. **`KERNELVERSION` export** -- required since 6.4 (`ec31f868ec674e`)

## LTO Kernel Support

For `CONFIG_LTO_CLANG=y` kernels, kpatch-build needs `vmlinux.o`. The pipeline
does a full kernel build with PGO profile data (`vmlinux.profdata`) before
invoking kpatch-build. Profile data URIs are in `facebook/bzl/constants.bzl`.

## RPM Details

- Module installs to `/var/lib/kpatch/<kernel-version>/`
- RPM requires the `kpatch` package (provides systemd service for boot-time loading)
- Module named `klp_<short_kernel_version>.ko`
- Current kpatch-build version: `0.9.11-0.2` (updated in commit `025b67441ed0`;
  cherry-pick this commit if the release branch doesn't have it yet)

## Tagging Convention

- Baseline tag matches the release branch name: branch `release-v6.16-fbk1` has baseline tag `v6.16-fbk1`
- Hotfix tag: append `-hotfix<N>` to the baseline tag, e.g. `v6.16-fbk1-hotfix1`
- For test KLP builds, use a big hotfix number (e.g. `hotfix123`) to make it obvious it's a test
- **Use a different number for each test build**, even when rebuilding the
  same patch after changes (e.g. `hotfix271`, `hotfix282`, `hotfix293`).
  Reusing the same hotfix number across rebuilds makes it hard to tell
  which `.ko`/`.rpm` corresponds to which version of the code
- To redo a test build, delete the old tag and create a new one with a
  **different** number: `git tag -d <old-tag> && git tag <new-tag>`
- The hotfix number is extracted and used in module naming and the dummy version-bump patch
- **Only use big hotfix numbers** (e.g. `hotfix123`, `hotfix271`) for test
  builds. Do NOT create official small-number tags like `hotfix2`, `hotfix3`.
  Let the user create those themselves when they are ready to promote a
  build to production

## Commit Hygiene

- **Only kernel code changes** in hotfix commits -- do not include
  documentation, prompt files, or other non-kernel files in commits
  between the baseline and hotfix tags
- **Preserve the original author and commit hash** when rewriting an
  upstream commit for livepatch compatibility. Always start with
  `git cherry-pick -x <hash>` to preserve the author and record the
  original hash, then `git commit --amend` to apply the rewritten changes
- **Annotate rewritten commits** -- when amending a cherry-picked commit
  with KLP rewrites, add a `[KLP: ...]` note at the bottom of the commit
  message (after the `cherry picked from` line) explaining what was
  changed and why. This makes it clear to reviewers that the patch was
  intentionally modified for livepatch compatibility
- **Squash related fixes** into one clean commit when iterating on a
  patch (e.g., initial patch + comment updates + `__LINE__` fixes should
  be one commit, not three)
- Keep the commit history between baseline and hotfix tags minimal and
  clean -- reviewers and the build system both benefit

## Step-by-Step: Building a KLP for a Specific Commit

**Before starting a build**, show the user the changes (e.g. `git log`
and `git diff` from the baseline tag) and ask them to review. KLP builds
take a long time, so catching issues early saves significant effort.
Skip this only if the user explicitly asks to build without review.

**Important**: The work must be done on the `release-<baseline-tag>`
branch, NOT on the baseline tag itself. For example, to patch
`v6.13-fbk6`, work on the `release-v6.13-fbk6` branch. If the branch
is not available locally, fetch it from `origin`.

### Pre-flight checks (do these BEFORE cherry-picking)

**1. Sync check:** Compare the local release branch with its upstream
tracking branch. If they differ, warn the user and ask them to confirm
before proceeding:
```bash
git fetch origin
git log --oneline origin/release-<baseline-tag>..release-<baseline-tag>   # local-only commits
git log --oneline release-<baseline-tag>..origin/release-<baseline-tag>   # remote-only commits
```
If either command produces output, tell the user:
> ⚠ Local branch `release-<baseline-tag>` is out of sync with
> `origin/release-<baseline-tag>`. Please verify and reconcile
> (e.g., `git pull --rebase`) before continuing.

**2. Existing hotfix check:** Look for existing hotfix tags on the
release branch:
```bash
git tag -l '<baseline-tag>-hotfix*'
```
If an official hotfix tag already exists (small number, e.g.
`-hotfix1`, `-hotfix2`), check whether the release branch HEAD
already includes those commits:
```bash
git log --oneline <baseline-tag>..<hotfix-tag>    # commits in the hotfix
git merge-base --is-ancestor <hotfix-tag> release-<baseline-tag> && echo "included"
```
If the hotfix tag is an ancestor of the release branch, the branch
already contains those changes — the new fix should be cherry-picked
**on top**. Tell the user:
> Found existing `<hotfix-tag>` with N commits already on the branch.
> The new fix will be built on top of those changes, so the resulting
> KLP module will include both the existing hotfix and the new fix.

If the hotfix tag is NOT an ancestor of the release branch (diverged),
warn the user and ask how to proceed.

### Cherry-pick and build

```bash
# 1. Switch to the release branch
git checkout release-v6.16-fbk1

# 2. Cherry-pick the fix commit (use -x to record origin)
git cherry-pick -x <commit-hash>

# 3. Cherry-pick any required KLP infrastructure commits
#    kpatch-build 0.9.11-0.2 update (required for newer kernels):
git cherry-pick -x 025b67441ed08e52   # Update kpatch-build binary to 0.9.11-0.2
#    The objtool revert is only needed for 6.16+ kernels:
git cherry-pick -x 9f393944288310c2   # Revert "objtool: Always fail on fatal errors"

# 4. Create a test hotfix tag (use big number for tests)
#    If building on top of an existing hotfix, this tag will naturally
#    include those earlier commits since they are already on the branch.
git tag v6.16-fbk1-hotfix123

# 5. Check out the hotfix tag (required for build infrastructure in klp.bzl)
git checkout v6.16-fbk1-hotfix123

# 6. Clean and build
sudo rm -rf buck-out/v2/
buck2 build $(facebook/build/buck-config) \
  -c klp.patch_to=v6.16-fbk1-hotfix123 //:klp-rpm

# 7. Copy build artifacts to klp-out/<arch>-<flavor>
mkdir -p klp-out/x86_64-regular
cp buck-out/v2/gen/linux/*/__klp-build__/out/*.ko klp-out/x86_64-regular/
cp buck-out/v2/gen/linux/*/__klp-rpm__/out/*.rpm klp-out/x86_64-regular/
```

To redo a test build after changes (use a **new** hotfix number):
```bash
# Amend/add commits, then create a NEW tag with a different number
git tag v6.16-fbk1-hotfix282
git checkout v6.16-fbk1-hotfix282
sudo rm -rf buck-out/v2/
buck2 build $(facebook/build/buck-config) \
  -c klp.patch_to=v6.16-fbk1-hotfix282 //:klp-rpm
```

## Debugging Build Failures

When `klp-build` fails, the build output includes the kpatch-build log inline.
Look for `create-diff-object` errors and `ERROR:` lines in the buck2 output.
Inside the container, the log is at `/root/.kpatch/build.log`.

Common failure patterns:
- **not checking out the hotfix tag** -- building from the release branch
  HEAD instead of the hotfix tag can fail because the build infrastructure
  (`klp.bzl`, `constants.bzl`) at HEAD may differ from what the hotfix tag
  expects. Always `git checkout <hotfix-tag>` before building.
- **thinlto partition diffs** -- with LTO kernels, hundreds of `vmlinux.o.thinlto.*`
  files may differ. `create-diff-object` can fail with `find_local_syms: couldn't
  find matching ... local symbols` when LTO shuffles symbols across partitions.
- **`safe.directory` git error** -- the container may complain about repository
  ownership in `/rw/compile`. This is a git safety check inside the container.
- **objtool fatal errors** -- the KLP module build may fail due to objtool
  treating warnings as fatal. Cherry-pick `9f393944288310c2` ("[META ONLY]
  [KLP ONLY] Revert 'objtool: Always fail on fatal errors'") into the hotfix
  branch to work around this.
- **LTO cascading changed functions** -- with LTO, kpatch-build will report
  many extra changed functions beyond what the patch touches (e.g., shmem,
  tlb, btrfs functions from a small mm patch). This is expected due to LTO
  cross-module optimization and does not prevent a successful build.
- **`runtime_ptr_USER_PTR_MAX` section error (all x86_64 flavors)** --
  on x86_64 (both regular and hardened), any changed or new function that
  calls `copy_from_user`, `copy_to_user`, `copy_struct_to_user`,
  `clear_user`, `put_user`, or `get_user` generates entries in a
  `.runtime_ptr_USER_PTR_MAX` section that `create-diff-object` does not
  support:
  ```
  ERROR: changed section .relaruntime_ptr_USER_PTR_MAX not selected for inclusion
  ```
  **Fix**: rewrite the patch to use `__copy_from_user`, `__copy_to_user`,
  `__clear_user` (which skip `access_ok()` and don't generate runtime_ptr
  entries). Open-code `copy_struct_to_user` with the `__` variants. Do NOT
  add an explicit `access_ok()` check -- it generates the same runtime_ptr
  entries. All runtime_ptr entries must be completely removed (partial
  removal fails). SMAP/PAN provides hardware protection regardless. See
  `patch-authoring-guide.md` "Runtime Constant Pointers" and
  `rewriting-patches.md` trick #16 for full details and rewrite patterns.
- **Patch glob drops patches numbered 0010+** -- the `klp.bzl` kpatch-build
  command historically used a glob like `000[3-9]-*.patch` that only matched
  patches 0003-0009. If the hotfix has more than ~7 commits (after the 2
  infrastructure patches), later patches are silently dropped. The fix
  (using `` `ls /tmp/patches/0*.patch | sort | tail -n +3` ``) is in newer
  branches; cherry-pick it if needed.
- **Always verify the `.ko` contains the expected functions** after a
  successful build. A build can succeed without including the fix if
  kpatch-build doesn't detect the function as changed:
  ```bash
  nm klp-out/<arch>-<flavor>/*.ko | grep '<expected_function>'
  ```

## Testing

Meta runs upstream livepatch selftests as part of kernel validation (listed in
`facebook/bzl/constants.bzl` SELFTESTS array). Tests are in
`tools/testing/selftests/livepatch/` and require `CONFIG_LIVEPATCH=y` and
`CONFIG_DYNAMIC_DEBUG=y`.

## Building for Multiple Kernel Branches

When the same fix needs to be applied to multiple release branches (e.g.,
`v6.11-fbk10` and `v6.13-fbk12`):

1. **Verify the affected code is identical** across branches before
   rewriting. Use `diff` to compare the relevant functions:
   ```bash
   diff <(git show v6.11-fbk10:fs/namespace.c | sed -n '1580,1610p') \
        <(git show v6.13-fbk12:fs/namespace.c | sed -n '1580,1610p')
   ```
   If identical, the same rewrite applies to both branches.

2. **Rewrite once, apply to all branches.** Cherry-pick + rewrite on
   each branch independently (`git cherry-pick -x` then `git commit
   --amend`). The rewritten diff should be identical across branches.

3. **Build all flavors for one branch before switching to the next.**
   This minimizes git checkout overhead and keeps artifacts organized.
   Remember to `git checkout <hotfix-tag>` for each build.

4. **Use per-branch subdirectories** in `klp-out/` to keep artifacts
   separated (see Build Commands above).

5. **Note aarch64 support varies by kernel version.** Older branches
   (e.g., v6.11 and earlier) only support x86_64 (2 builds), while
   newer branches support all 3 arch/flavor combinations (3 builds).
